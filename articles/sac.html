Поиск как код

Исходная работа: Perplexity, "Rethinking Search as Code Generation", Perplexity Research, 2026.

ИИ-агент, выполняющий сложную задачу, может сделать сотни или тысячи поисковых запросов за несколько минут. Обычный поисковый API на такую нагрузку и такой характер использования не рассчитан — он спроектирован иначе и для другого пользователя.

Почему классический поиск не подходит для агентов?

Поисковые системы изначально строились для человека: он вводит запрос и получает предсказуемый результат — фиксированное число документов, отсортированных по релевантности. Это устройство годами оптимизировали под скорость и привычность интерфейса, а не под тонкий контроль над самим процессом поиска.

Когда потребителем поиска стали LLM (large language model — большая языковая модель), большинство ИИ-ориентированных поисковых систем унаследовали тот же контракт: принять запрос, прогнать его через фиксированный пайплайн (pipeline — заранее заданную последовательность обработки), вернуть готовый набор результатов. Сама архитектура не изменилась — изменился только тип клиента.

Авторы называют три конкретных следствия этой негибкости. Первое — грубый контекст (coarse context): модель не может получить данные, подогнанные под конкретные требования именно этого запроса. Эндпоинты, оптимизированные под полноту охвата (recall), приносят вместе с нужным и лишнее; а если задаче нужны разные стратегии поиска сразу, каждую приходится вызывать по очереди, что стоит времени и добавляет шум при объединении результатов. Второе — ограничение доменных знаний: у модели есть собственные знания, навыки и память, которые могли бы направлять стратегию поиска, но жёсткий интерфейс не даёт параметров, через которые это знание можно было бы применить. Третье — неэффективный поток управления (control flow): задачи, которым нужны параллельный запуск нескольких запросов (fan-out), параллельная загрузка страниц или удаление дублей (deduplication), заставляют модель делать это вручную, ход за ходом, что добавляет задержку и, по формулировке авторов, «засоряет контекст модели шумным промежуточным состоянием».

Идея: поиск как код

Ответ авторов — Search as Code (SaC, «поиск как код»): не фиксированный сервис, возвращающий готовый набор результатов, а набор программируемых примитивов (primitives — минимальных строительных блоков), из которых модель сама собирает стратегию поиска под конкретную задачу, генерируя и исполняя Python-код в защищённой песочнице (sandbox — изолированной среде исполнения).

Разница принципиальная: раньше стратегию поиска фактически выбирал бэкенд поисковой системы, ограничивая модель заранее предусмотренными эндпоинтами. В SaC стратегию выбирает сама модель, а бэкенд предоставляет ей строительные блоки и среду для их сборки.

Три слоя архитектуры

SaC состоит из трёх слоёв. Модели выступают «управляющим слоем» (control plane) — они рассуждают о задаче и генерируют код, который собирает конвейер поиска. Вычислительные песочницы обеспечивают «детерминированные вычисления через защищённую среду исполнения кода» — именно они выполняют поток управления, батчинг (пакетную обработку запросов), повторные попытки, фильтрацию, объединение и агрегацию данных. Agentic Search SDK предоставляет весь поисковый стек Perplexity в виде компонуемых примитивов — от низкоуровневого извлечения данных до высокоуровневого семантического разбора.

Сам SDK — не обёртка над старым поисковым API, а полная переработка: команда разобрала существующий поисковый стек на модульные, компонуемые примитивы. Готовые высокоуровневые конвейеры остаются доступны как сокращённая запись для типовых сценариев поиска, но модель может обойти их и собрать свою комбинацию примитивов напрямую, если задача требует более тонкого контроля.

Помимо сборки конвейера, у генерируемого кода есть вторая роль — заполнять пробелы: если в поисковом стеке или SDK не хватает какой-то возможности, модель может написать недостающий кусок логики прямо в коде, а не ждать, пока такая возможность появится в SDK как отдельная функция. Это позволяет держать сам SDK минимальным, оставляя в нём только самые фундаментальные примитивы.

Решения внутри: язык, память между шагами, обучение модели

В качестве языка для песочницы выбрали Python — по внутренним тестам он оказался «наиболее естественным выбором благодаря распространённости и экосистеме». Отдельно команда держит постоянно работающий «итеративный цикл автоисследования» (autoresearch loop), который непрерывно предлагает улучшения SDK, проверяемые по задержке, качеству генерируемого кода и результативности на задачах.

Отдельная инженерная развилка — как переносить промежуточное состояние между несколькими ходами модели. Команда сравнила два подхода. Постоянная файловая система с явной сериализацией (serialization — преобразование данных в форму, пригодную для сохранения) даёт модели прямой и явный контроль над тем, как состояние передаётся между ходами, и обеспечивает прослеживаемость за счёт явной идентификации данных — но платит за это задержкой и затратами контекста на генерацию кода сериализации. REPL-режим (Read-Eval-Print Loop — интерактивная среда, сохраняющая состояние между командами) держит саму среду исполнения живой между ходами, так что переменные, определённые на предыдущем шаге, доступны без всякой сериализации — это оказалось экономнее по токенам, но тестирование показало, что на особенно длинных траекториях сериализация через файловую систему надёжнее.

Команда выбрала файловую сериализацию, исходя из теории, что «требование явно, декларативно передавать состояние помогает модели эффективнее им управлять». Важная деталь: сами авторы называют это теорией, а не доказанным механизмом — притом что REPL-режим по их же данным экономичнее по токенам. Это единственное место в статье, где команда явно признаёт, что решение принято на основе гипотезы, а не подтверждённого результата.

Ещё одна практическая проблема — у кастомного SDK нет никакого представления в данных, на которых предобучалась модель, значит, о его существовании модель попросту не знает заранее. Решение — точно настроенные «Agent Skills» (навыки агента): компактные, обобщаемые инструкции с примерами использования, которые учат модель компоновать примитивы SDK в сложные схемы. Итоговые версии таких файлов — меньше 2000 токенов в корневом SKILL.md.

Как читать цифры дальше

Прежде чем переходить к результатам, стоит явно оговорить, что это за цифры. Все показатели ниже — из собственной оценки Perplexity собственной системы, опубликованной на исследовательском сайте компании, а не в независимо рецензируемом издании. Это не делает цифры неверными, но это другой уровень доказательности, чем независимо проверенное исследование, и дальнейший текст стоит читать с поправкой на это. Кроме того, статья не раскрывает ни размер выборки, ни статистическую значимость сравнений, ни то, насколько сопоставимыми усилиями были настроены конкурирующие системы — OpenAI Responses, Anthropic Managed Agents, Exa Agent и Parallel Tasks — для этого сравнения.

Кейс CVE и формальное сравнение

В одной из практических задач агентам нужно было найти и охарактеризовать более 200 CVE (Common Vulnerabilities and Exposures — общеотраслевых идентификаторов уязвимостей) высокой степени серьёзности, сославшись на рекомендации вендоров и привязав конкретные исправления к конкретным уязвимостям. SaC достиг 100% точности, а расход токенов при этом упал на 85,1% относительно собственной версии Perplexity без SaC. Все протестированные системы конкурентов набрали меньше 25%.

Подход агента состоял из трёх фаз: сначала параллельный запуск запросов (fan-out) по разным форматам рекомендаций вендоров с использованием точных фразовых запросов, ограниченных конкретным сайтом; затем — синтез уточняющих запросов там, где покрытие оказалось скудным, с планированием на основе самой модели; и наконец — проверка привязки CVE к версии через структурированное извлечение данных и удаление дублей.

Отдельно провели формальное сравнение на пяти бенчмарках: DeepSearchQA (DSQA), BrowseComp, Humanity's Last Exam, WideSearch и новом бенчмарке WANDR — он посвящён сложным задачам «широкого исследования», требующим слаженной работы поиска, вычислений и рассуждений модели одновременно. Сравнивали пять систем: Perplexity (SaC), OpenAI Responses, Anthropic Managed Agents, Exa Agent и Parallel Tasks.

SaC обошёл всех четырёх конкурентов на четырёх из пяти бенчмарков. На DSQA — 0,871 против 0,733 у OpenAI и 0,815 у Anthropic. На BrowseComp — 0,805 против 0,720 у OpenAI. Самый заметный разрыв — на WANDR, где реализация SaC обошла следующую по качеству систему в 2,5 раза.

Отдельно от сравнения с конкурентами интересен эффект самой архитектуры: при сравнении SaC с предыдущей, не-SaC версией самой Perplexity прирост составил от 19,77 процентного пункта на DSQA (относительный прирост 29%) до 12,00 процентного пункта на WANDR (относительный прирост 45%).

По соотношению цены и качества: на низком уровне «усилия рассуждения» SaC показывал результат не хуже всех не-SaC систем, но по более низкой цене; на среднем уровне — превосходил не-SaC подходы, оставаясь дешевле 1 доллара за задачу; на высоком уровне достигал максимального качества при цене, которую авторы называют по-прежнему конкурентной.

Что это значит и куда дальше

Авторы помещают эту работу в более широкую рамку: у традиционного программного обеспечения в основе — детерминированное выполнение инструкций на CPU, а у современных моделей — «рассуждение в пространстве токенов, которое может как следовать инструкциям, так и порождать их». По их мнению, лучшие будущие системы будут сочетать оба вида вычислений, а не выбирать между ними, и поиск предлагается как «естественный полигон для такой гибридной архитектуры».

В этой картине модель решает, какие именно данные нужны и как разрешать неопределённость, а детерминированная среда исполнения берёт на себя батчинг, параллелизм, фильтрацию, ранжирование и агрегацию. Поисковая инфраструктура при этом описывается как «универсальный слой ввода-вывода», способный выдерживать тысячи операций в минуту.

Среди направлений дальнейшей работы авторы называют совместную оптимизацию цикла автоисследования, обучение моделей напрямую на низкоуровневых примитивах и «совместную эволюцию дизайна SDK прямо в процессе обучения модели». На момент публикации SaC уже развёрнут в Perplexity Computer и Agent API, а оптимизация всех трёх слоёв архитектуры продолжается.

Глоссарий

SDK (software development kit, комплект для разработки) — набор инструментов и компонентов, которые разработчик или, в данном случае, модель использует для построения программ; в статье — Agentic Search SDK, представляющий поисковый стек Perplexity в виде отдельных компонуемых блоков.

Sandbox (песочница) — изолированная среда исполнения кода, в которой сгенерированный моделью код может безопасно запускаться, не имея прямого доступа к остальной инфраструктуре.

Control plane (управляющий слой) — часть системы, принимающая решения о том, что и как должно произойти, в противоположность слою, который эти решения непосредственно исполняет. В SaC роль управляющего слоя играет модель.

Pipeline (конвейер, пайплайн) — заранее заданная последовательность шагов обработки данных, через которую проходит запрос от начала до конца.

Fan-out — параллельный запуск нескольких похожих операций (например, поисковых запросов) одновременно, вместо того чтобы выполнять их одну за другой.

Deduplication (дедупликация) — удаление повторяющихся записей из набора данных, например одинаковых результатов, найденных разными запросами.

REPL (Read-Eval-Print Loop) — интерактивная среда исполнения кода, которая читает команду, выполняет её, печатает результат и ждёт следующую, сохраняя при этом текущее состояние (переменные, объекты) между командами.

Serialization (сериализация) — преобразование данных (например, переменных программы) в форму, которую можно сохранить в файл или передать между процессами, а затем восстановить обратно.

Autoresearch loop (цикл автоисследования) — по описанию статьи, непрерывно работающий процесс, который предлагает улучшения SDK и проверяет их по метрикам задержки, качества генерируемого кода и результативности на задачах.

CVE (Common Vulnerabilities and Exposures) — общеотраслевая система идентификаторов известных уязвимостей программного обеспечения, используемая индустрией кибербезопасности для однозначной привязки уязвимости к конкретному программному продукту и его версии.

Benchmark (бенчмарк) — стандартизированный набор задач для сравнения разных систем между собой на одних и тех же условиях. В статье используются DeepSearchQA, BrowseComp, Humanity's Last Exam, WideSearch и WANDR.
